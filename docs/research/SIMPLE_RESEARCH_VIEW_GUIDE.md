# Simple Research View Guide

## Purpose

Simple Research View is the guided, plain-language page for understanding what structured patient data exist, what the current model actually uses, what has been simulated, and what conclusions remain out of scope.

It is a research simulation view only. It is not a treatment recommendation, not clinically validated, and causal effect not identified.

## What Each Card Means

- Data status: whether structured longitudinal records exist across the main input blocks.
- Model status: whether a mathematical starting state exists and whether deeper diagnostics are available.
- Scenario status: whether completed simulated schedules exist for comparison.
- Main limitation: the most important current reason to stay cautious when reading the outputs.

## How To Read Data Status

- `enough` means the block has enough structured records to be informative for the current workflow.
- `partial` means some useful records exist, but the block is incomplete.
- `missing` means the block does not yet provide structured information for the current workflow.

Each data block also explains:

- what the block means in plain language,
- which fields are used,
- whether the model uses it,
- why it matters,
- what is missing,
- the next visible action.

## How To Read Data Classification Labels

Every drilldown item in the page is labeled as one of these types:

- `RAW STRUCTURED`: entered or extracted into structured patient records.
- `DERIVED`: calculated from structured rows.
- `SIMULATED`: generated by the mechanistic model.
- `HEURISTIC`: a rule-based research score or prototype signal.
- `MISSING`: not available in structured form.

These labels answer a basic question for every visible value: is this a recorded fact, a calculation, a model-generated output, a heuristic summary, or a gap?

## What Each Data Block Means

The page now includes a dedicated `What each data block means` section.

Each block explains:

- what the block is in plain language,
- where the rows came from,
- whether the model uses the block,
- which model section uses it,
- what missing rows mean,
- what to do next if it is missing,
- how to inspect source rows without reading JSON.

Use this section before interpreting any scenario card.

## How To Inspect Source Rows

Each data block has an `Inspect details` control.

The drilldown shows:

- a per-field explanation card,
- the technical field names,
- the model section that uses the field,
- the latest structured or derived source rows,
- a plain-language meaning for each row.

The simple page does not expose raw JSON in this drilldown.

## How To Read Missing Data

Missingness messages are concrete by design.

- If a field exists, the page tells you how many structured rows are available.
- If a field is missing, the page names the missing field directly.
- If timing fields are missing from therapy rows, the page explains that schedule-to-exposure interpretation becomes weaker.
- If AST or ALT are missing, the page explains that toxicity interpretation is weaker.
- If no mathematical starting state exists, the page explains that scenario results cannot yet be anchored to a current patient-specific model state.

The goal is to make missing data actionable instead of vague.

## How To Know Whether The Model Uses A Value

The `What the model actually uses` table and each drilldown card both answer this question.

- `Used by model: Yes` means the value is consumed by at least one research workflow step.
- `Used by model: No` means the value is a displayed output or diagnostic, not an input.
- `Used in` names the specific section, such as initialization, calibration, scenario simulation, toxicity constraint, uncertainty, backtesting, or robustness.

## How To Read Scenario Comparison

The scenario section simplifies each run into:

- schedule meaning in plain English,
- exposure pattern,
- disease-control signal,
- healthy-tissue strain,
- toxicity signal,
- uncertainty range,
- plain-language interpretation.

Each card now also includes `Why this result?`, which explains:

- how the recorded schedule became an exposure pattern,
- what changed in the simulated branch,
- what output changed,
- what happened to the prototype toxicity signal,
- what the stored uncertainty or ranking-stability summary says.

Use the hidden technical-metrics toggle only when you need the field names used in the Scientific Cockpit.

## How To Read Uncertainty

The simple page uses the phrase **uncertainty range** instead of dense diagnostics.

- A narrow range means the stored output changes less under the current perturbation checks.
- A wide range means the stored output changes more under those checks.
- This is still a research diagnostic, not a clinical confidence interval.

## What Conclusions Are Allowed

- The model can compare simulated trajectories under different schedules.
- Some schedules produce different exposure profiles.
- Some outputs are more uncertain than others.

## What Conclusions Are Forbidden

- A model comparison identifies a clinically preferred treatment.
- This proves clinical superiority.
- This estimates a causal effect.

## How To Escalate To Cockpit Or Developer Console

- Stay in Simple Research View when you need the guided story.
- Open Scientific Cockpit when you need formulas, uncertainty details, backtesting, sensitivity, robustness, or provenance.
- Open Developer Console when you need internal validation, privacy checks, artifact checks, or debugging.
- Open Glossary when a technical term needs decoding.

The intended escalation path is:

- `Simple Research View -> Scientific Cockpit -> Developer Console`
